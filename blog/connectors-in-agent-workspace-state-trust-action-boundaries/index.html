此前讨论 Workspace 时，问题相对单纯：本地编辑器掌握文档内容，Agent 通过工作空间认识当前文件、编辑位置和可用动作。那套方案解决的是 Agent 的交互底座，让它不再只面对用户输入的一句话，而能理解自己正在什么环境中工作。

连接器进入之后，问题发生了变化。

Notion、Google Drive、Slack、GitHub 或 Linear 中的资源不由当前产品直接管理。它们有各自的账号、权限、数据结构和更新时间。用户可以在外部平台继续修改内容，其他协作者也可能同时操作。Agent 本轮读取到的内容，与远程平台此刻保存的内容，未必完全相同。

这时，设计重点已经不再是“怎样把远程数据交给 Agent”，而是“Agent 的上下文应该以谁为主体”。

连接器可以提供数据，却不适合作为上下文主体。一次对话可以使用多个连接器，也可能同时使用本地文档、上传文件和历史任务结果。对话本身同样不合适，它的生命周期太短，无法保存用户长期选择的资源、同步进度和未完成动作。Agent Runtime 只服务于当前执行，结束后便会释放，也不能成为这些状态的归属方。

真正持续存在的是工作空间。

工作空间记录用户正在处理什么、允许 Agent 使用哪些资源、各项资源来自哪里、最后一次读取发生在什么时间、有哪些修改正在等待处理、哪些长期任务还没有结束。连接器向工作空间提供外部资源，当前 Agent 再从工作空间取得一份与本轮任务有关的视图。

因此，我对连接器上下文的基本判断是：

工作空间是主体，连接器是资源来源，Agent Runtime 是当前执行者，对话框只是交互入口。

这个判断并非为了让架构显得完整，而是来自用户真实工作的持续时间。Web 端的 Agent 通常只能感知上传文件和当前 prompt，看不到文件之间的关系、先前做过的修改、跨应用的操作结果，也不知道某项任务为什么停在现在这个位置。真实工作会跨文件、跨应用、跨权限持续数小时，甚至数天。Agent 若只依赖对话文本，每次开始都要重新猜测用户正在做什么。

连接器进入工作空间的意义，正是把这些长期关系变成 Agent 可以理解的工作环境。

本地编辑器与远程连接器应在共同边界中保留差异

此前的 Workspace 工作空间状态管理与交互入口设计，已经建立了本地编辑器与 Agent之间的交互基础。Agent可以读取当前文档，理解片段位置，提出修改，并在用户确认后更新内容。这套设计说明了 Agent如何参与写作，却没有处理远程资源的时间、权限和所有权问题。

本地编辑器的内容由当前产品直接管理。用户修改文字后，系统能够立即获得新状态。远程连接器的内容由外部平台管理，当前产品看到的内容可能落后，写入也需要等待外部平台确认。

因此，两者可以共享工作空间资源这一层表达：它们都有资源身份、标题、内容引用、可用动作和当前版本。两者不能共享完全相同的更新语义。

本地编辑器可以直接提供当前状态，远程资源通常提供最近一次工作空间视图和按需读取能力。本地修改完成后，结果可以立即回到编辑器；远程修改还要经历版本核对、外部提交和结果刷新。本地权限来自当前产品，远程权限同时受外部授权和用户选择影响。

把本地编辑器视为一种特殊的工作空间资源来源是可行的。共同层只规定 Agent怎样发现资源、读取资源、理解能力和提出动作。每个来源自行说明内容从哪里取得、版本怎样判断、修改怎样完成。

这种共同边界也为后续连接器留下空间。Agent核心无需理解 Notion数据库、Slack频道、GitHub Issue 或 Linear项目的全部细节。它只需要知道当前工作空间有哪些资源，这些资源在任务中扮演什么角色，可以读取哪些内容，允许提出哪些动作，当前资料是否过期。

连接器之间的差异通过能力表达。Notion页面可能支持更新正文，Slack消息可能只允许发送或回复，GitHub资源可能提供评论、标签和状态变化。通用层不把它们压缩成一个含混的“写入”，而是让每个连接器说明自己真实提供的动作及其影响范围。

系统能否拓展到下游，取决于 Agent核心是否始终围绕工作空间和当前任务组织，而不是把某个平台的对象写入通用流程。新连接器需要把自己的资源、权限、版本和动作翻译成工作空间能够理解的形式。Agent的阅读、确认和任务流程不需要因平台变化重新设计。

把全部外部内容塞进模型上下文，看起来省去了后续读取动作，实际会制造新的混乱。

上下文应该围绕写作者正在做的事

此前的本地编辑器方案有一个明确前提：用户、文档和 Agent 位于同一个产品环境中。用户正在编辑哪篇文章，编辑器当前保存了什么内容，Agent应该读取哪个片段，都可以从 Edit Session 中得到答案。此时，Agent上下文围绕当前文档组织是合理的，因为文档状态由本地编辑器直接管理，用户的操作也会立即反映在同一份状态中。

连接器加入后，这个前提发生了变化。Notion 页面不属于本地编辑器，内容可以在产品之外被修改；用户对资源的选择可能持续数月，一次 Agent 对话只存在几分钟；同一个远程页面还可能同时出现在多个项目、多个对话和多个写作任务中。继续让 Agent Session 管理连接器状态，会让长期资源关系依附于短期对话。反过来，若直接以 Notion 连接器为中心组织上下文，页面、数据库之类的平台概念又会进入 Agent 的通用工作方式，未来接入 Google Drive、Slack、GitHub 或 Linear 时，只能不断增加新的例外。

因此，连接器进入工作空间后，Agent上下文的中心对象应当是写作者当前正在进行的工作。

工作空间记录这项工作持续存在的部分：当前稿件、选中的资源、资源在任务中的用途、最近一次可靠读取、尚未处理的修改以及仍在执行的后台任务。Agent的一次运行只取得这些状态在当前时刻的视图。连接器负责说明资源来自哪里、允许做什么、内容有多新；它不决定整段上下文如何组织。

这种设计保留了写作过程的中心位置。用户连接 Notion，不是为了让 Agent研究一个连接器，而是为了写文章、整理材料、核对事实或修改方案。连接器只是资源来源。Agent首先需要知道用户此刻在写什么，然后才需要知道哪些外部资料与这项工作有关。

同一个页面在不同任务中的用途也可能不同。它可以是一份只读参考资料，也可以是正在修改的目标文档，还可以是一份用于比较语气的范例。只记录页面内容还不够，工作空间需要记录用户为什么把它放进当前任务。资源的用途会直接影响 Agent的动作：参考资料可以摘取和引用，目标文档可以提出修改，范例可以分析写法，却不应被当成当前稿件。

这说明工作空间上下文不只是资源清单。它还需要表达资源与当前工作的关系。Agent拿到一张地图时，应当看到当前写作对象、相关资料、资料用途、读取时间和允许动作。正文继续按需读取，资源在任务中的位置则应当从一开始就说明。

写作者的思考过程应当成为资源交互的主线

写作不会按照“连接资源、读取内容、生成答案”一次结束。真实过程更接近反复移动：先形成一个模糊问题，再寻找相关资料，从资料中选出片段，回到稿件中试写，发现论述不足后重新查找，最后修订文字和引用。

连接器产品需要支持这种往返过程。它不应把外部资料设计成一次性输入，也不应让 Agent每次都从整个资源库重新开始。

工作空间可以保存用户在写作过程中形成的选择。某个页面为什么被加入当前项目，哪一段内容被引用，Agent根据它形成了什么笔记，用户是否接受了这条理解，这些信息比“连接器中有一百个页面”更接近实际写作。

例如，用户正在写一篇产品回顾。他从 Notion中选择一份早期方案、一份用户反馈和一份上线记录。三份资料的用途不同：早期方案用于恢复当时的目标，用户反馈用于检查结果，上线记录用于确认时间。Agent若只看到三个页面标题，很难判断怎样使用；工作空间若记录了这些用途，Agent就能围绕当前文章组织材料。

写作过程中的中心对象仍然是当前稿件。外部资源可以提供事实、例子、背景和语言参考，也可能成为修改目标。产品需要明确区分这几种关系，避免 Agent把参考资料当成待改文件，或把临时笔记当成原文事实。

当 Agent从外部资源中提取内容时，最好形成带来源的工作笔记。笔记可以被重写、组合和删减，来源引用继续保留。原文发生变化时，系统可以指出哪些笔记可能需要重新检查。这样，写作者能够发展自己的思考，同时知道这些判断最初从哪里来。

这也是快照真正参与写作的方式。快照的价值不只在防止覆盖，它帮助写作者理解自己的判断建立在什么时间点。文章写了几天后，用户重新打开项目，系统可以说明某段分析使用的是三天前的资料，而对应页面昨天已经更新。用户再决定是否需要重新阅读。

Agent上下文也应随着写作阶段变化。探索阶段需要资源目录、搜索和摘要；形成观点后，只需要少量被选中的片段与工作笔记；修改稿件时，当前文本和相关来源应处于主要位置；准备写回远程平台时，再加入目标版本、修改范围和确认状态。

这比固定拼接一份大型上下文更符合写作者的思考方式。上下文不是资源数量的总和，而是当前工作所需信息的选择结果。

冲突：原来的修改为什么失去了执行条件

Agent 读取页面后，用户可能继续在 Notion 中编辑。其他协作者也可能修改同一内容。另一个 Agent 对话可能基于相同旧版本提出新的改动。

这不是偶发错误，而是远程协作中的常态。

当目标内容已经变化，原修改意图不能继续直接提交。产品需要保留三份内容：Agent 最初读取的版本、远程平台当前版本，以及 Agent 准备提交的修改。

用户查看这三份内容后，可以重新生成提议，保留远程版本，重新应用部分修改，或自己整理最终文本。

产品在这里首先要避免静默覆盖。自动合并并非所有内容都适用，特别是写作材料。同一句话的两种改法可能都没有结构错误，却表达了不同意图。系统很难仅凭文本差异判断用户希望保留哪一种表达。

冲突也不应只存在于当前聊天消息里。用户可能暂时离开，几小时后再处理。修改意图和冲突记录需要属于工作空间，使用户能够在后续对话或独立页面继续处理。

解决冲突后，新的资源状态先回到工作空间。后续 Agent 再依据更新后的版本继续工作。这样，下一次对话不必依赖之前聊天文本中的临时说明。

写作者的思考如何进入资源交互

写作不是从一个文件读取信息，再向另一个文件输出结果。写作者会在草稿、资料、批注、旧版本和未解决问题之间来回移动。

一段产品方案可能从会议记录开始，随后引用用户访谈，连接到一个 Notion 数据库，再与本地草稿中的旧结论比较。作者会保留某句话，删除另一段，暂时搁置一个判断，几小时后从其他资料中找到新的解释。

这些变化构成了写作过程中的隐性知识。

普通对话框通常只保留用户说了什么、Agent 回答了什么。它看不到用户为什么打开某个文件，为什么同时比较两份材料，也不知道上一轮修改已经被拒绝，某项资料仍在后台导入。

工作空间需要保存这些与工作相关的关系。

当前草稿是主要写作对象，外部页面是参考资料，评论记录尚未解决的问题，修改意图记录准备采取的动作，任务结果说明哪些资料已经准备完成。Agent 不必知道用户每一次鼠标操作，却应知道当前任务依赖哪些资源，以及之前发生过哪些会影响本轮判断的动作。

这也意味着 Workspace Context 不应变成外部资料的全文集合。它更适合表达当前写作环境：

正在处理哪份文档。

有哪些相关资料已经挂载。

哪些资源刚被读取。

内容是否可能过期。

有哪些修改正在等待确认。

后台任务是否产生了新的结果。

这些信息让 Agent 理解当前工作位置。正文仍然按需读取，操作记录只保留与当前任务有关的部分，较早内容可以压缩成摘要和引用。

写作者也应当能查看并调整这份上下文。他可以知道 Agent 本轮使用了哪些资料，移除不相关来源，要求刷新某个页面，固定使用某个版本，或把本轮产物保存回工作空间。

这种可见性比单纯增加模型上下文长度更重要。用户能够检查 Agent 的依据，才可能判断它的回答是否值得继续使用。

本地编辑器和外部连接器如何进入同一个工作空间

本地编辑器与远程连接器可以共享一部分资源语言：资源身份、标题、引用、内容版本、读取能力、修改提议和操作记录。

这能让 Agent 使用相近的方式理解本地草稿和外部资料。它可以先查看资源地图，定位目标，读取内容，提出修改，再根据来源选择具体执行方式。

两者的差异不能被抹平。

本地编辑器由当前产品直接管理，用户输入后，产品通常能够立即获得新状态。远程资源由外部平台管理，读取受到网络和权限影响，写入也需要等待远程结果。外部协作者还可能在 Agent 工作期间改变内容。

因此，本地编辑器可以被视为一种工作空间资源来源，却不应被强行描述成普通远程连接器。共同抽象只覆盖资源引用、上下文展示和动作提议。数据所有权、版本核对、认证方式和提交语义仍由各自来源保留。

这一边界也决定了未来连接器如何接入。

Google Drive 提供文件和目录，Slack 提供频道与消息，GitHub 提供仓库、Issue 和 Pull Request，Linear 提供项目与任务。它们不能全部被缩减成同一种“文档”。

工作空间需要理解共同信息：资源是谁、来自哪里、现在能否读取、有哪些动作、内容是否新鲜。具体资源仍保留自身类型和操作方式。Slack 消息能够回复，GitHub Issue 能够关闭，Linear 任务能够改变状态，Notion 页面能够更新区块。能力由连接器声明，Agent Runtime 无需预先了解每个平台的全部细节。

这样，新连接器接入时，核心 Agent 流程保持不变。它仍然从工作空间获取资源视图，按需读取，生成操作提议，等待必要确认，随后取得结果。连接器负责把这些共同动作翻译成外部平台能够理解的请求。

Notion 可以成为第一个验证对象，不应成为通用模型本身。通用设计若直接使用 Page、Block、Database 作为核心概念，后续接入 Slack 和 GitHub 时会不断增加例外。工作空间应使用资源、引用、版本和能力等共同概念，平台特有信息保留在资源类型与能力描述中。

用户需要看见的连接器状态

连接器状态最终要回到产品界面。内部状态再完整，用户看到的仍然只有一个绿色圆点，设计价值便无法体现。

设置页应分别说明账号、资源范围和资源准备情况。账号已授权但没有选择资源时，应明确显示“尚未选择资源”。资源正在建立目录时显示处理进度。最近一次刷新失败且旧内容仍可使用时，应说明当前使用的是哪次成功结果。

对话界面应让用户知道本轮 Agent 使用了哪些连接器资源。回答依赖旧内容时，应显示读取时间。外部平台暂时不可用时，继续使用旧内容需要明确说明。涉及修改的动作，要展示目标、范围、版本和确认状态。

工作空间还需要集中展示正在执行的长期任务、等待处理的修改和版本冲突。用户离开某次对话后，仍能回到这里继续处理。

用户无需了解内部接口和存储方式。他只需理解当前发生了什么：

账号是否可用。

哪些资源已经进入工作空间。

本次 Agent 使用了什么。

内容是否可能过期。

哪些操作正在等待自己决定。

远程结果是否已经确认。

这六项信息构成了连接器产品的信任基础。

从对话框走向操作系统级入口

今天许多 Web Agent 的交互仍然围绕 prompt 和上传文件展开。用户把资料交给模型，等待一次回答，再把结果手工复制回原来的应用。

这种方式适合短任务。真实工作并不总能在一个对话回合中完成。

资料分布在不同应用，权限由不同账号管理，文件之间存在引用关系，操作结果会改变后续判断，长期任务还需要在用户离开后继续执行。仅靠对话历史无法表示这些事实。

Agent 需要一个持续存在的工作环境。这个环境知道资源在哪里，哪些内容可以使用，当前版本是什么，之前采取过什么动作，还有哪些任务尚未结束。

所谓操作系统级入口，并不是要求产品复制传统操作系统的界面。它指向一种更完整的工作方式：Agent 可以发现资源、取得受限能力、观察状态变化、提出动作、等待确认、继续长期任务，并把结果保存为下一次工作可以直接使用的状态。

连接器在其中承担外部资源入口，工作空间负责组织用户的长期工作关系，Agent Runtime 负责当前执行。四层架构分别解决访问、依据、动作与持续时间的问题。

认证层回答系统能否代表用户进入外部平台。

数据层回答 Agent 此刻能够依据什么。

操作层回答一次提议怎样成为真实变化。

任务层回答工作如何越过当前对话继续完成。

当这四个问题得到明确回答，连接器才不再是设置页中的一个授权按钮。它开始成为工作空间的一部分，让写作者能够在本地草稿、外部资料、历史动作和长期任务之间持续工作。

连接器设计的最终目标，也不在于让 Agent 读取更多内容。真正需要建立的是一种可以被用户检查的工作关系：Agent 看见了什么，为什么能够看见，依据的是哪个时间点，准备改变什么，结果是否已经发生。

这些问题得到清楚回答之后，用户才可能把跨文件、跨应用、跨权限的长程任务交给 Agent。
